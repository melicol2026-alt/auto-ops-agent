# 06 汇报与迭代机制

## 一、汇报原则

用户不需要知道你"做了什么动作"，需要知道：
**发生了什么结果、有什么风险、接下来会怎样。**

**禁止**：贴大段日志、罗列命令执行过程、把报错原样抛给用户。
**必须**：如实转述失败（不美化）、给出影响、给出你接下来要做的动作。

## 二、每日汇报模板

```
## 今日运营汇报（{日期}）

**发布**：{篇目 id 与标题} ｜ 状态：已发布 / 试跑待检查 / 被拒发（原因）
**互动**：点赞 {n} ｜ 收藏 {n} ｜ 评论 {n}（当日累计 vs 上限）
**异常**：无 / {如实描述，含风控熔断、选择器失效、未登录等}
**队列**：剩余待发布 {n} 篇 ｜ 评论池剩余 {n} 条
**下一步**：{我接下来要执行的动作}
```

门禁命中时必须带一句明确的提示："该篇在等待确认，确认后说一句通过即可放行，放行后自动发布。"

## 三、每周汇报模板

```
## 本周运营复盘（{日期区间}）

**数据**：统计口径与范围、样本量
**表现**：各支柱/题型表现差异
**判断**：表现好与差的内容，差异假设（明确区分相关性与因果）
**动作**：放大 / 优化 / 暂停 / 待核实
**需求**：稀缺度 TOP 变化，下周优先切入的 3 个词
**下周**：选题 4–5 个、只验证的 1–2 个变量、素材清单、发布日历
**合规**：本周高风险表达汇总与替换规则
```

样本不足时必须明确写"样本不足，以下仅为假设"，并给出补数清单。

## 四、自动化 prompt 模板（关键：写死不可违反的边界）

每个定时自动化必须包含四段：

```markdown
【任务】{要做什么，含具体命令}

【完成后】{读什么文件、输出什么格式的汇报}

【边界（不可违反）】
- 不得修改 config.py 的频次上限或风控阈值
- 不得绕过合规预检
- 不得自行修改门禁配置或把篇目加进放行名单
- 评论只从预生成队列取用，队列用尽时只报告不足，不得现场编造
- 若浏览器未登录，如实报告需要用户首次扫码

【失败处理】
脚本报错时如实报告，不要静默跳过，不要用估算数据填充。
```

**边界段不是装饰** —— 它防止后续执行者（包括未来的自己）为了完成任务而提高频次或绕过检查。

## 五、回流机制（L6 → L2）

复盘结论必须**写回可供选题读取的文件**，否则迭代断链：

```
周复盘 → 更新 稀缺度报告 / 支柱配比 / 合规替换规则表
每日内容包 → 读取上述文件 → 选题
```

每次内容交付末尾写一行**需求依据**：
> 需求依据：本篇选题来自需求词「{词}」，稀缺度 {n}，采集日期 {date}

这样每篇内容都能追溯到数据，而不是凭感觉。

## 六、自动化排期建议

| 时间 | 任务 | 说明 |
|---|---|---|
| 07:30 每日 | 需求信号快速采集 | 零登录，5 分钟 |
| 08:30 每日 | 内容策划包 | 读稀缺报告 + 证据库 + 出成稿 |
| 09:40 每日 | 发布 + 互动 | 主发布窗口 |
| 14:50 每日 | 互动 | 低频拟人 |
| 20:40 每日 | 互动 + 当日小结 | 收口，检查队列与评论池余量 |
| 周日 20:00 | 需求信号全量采集 | 8–15 分钟，出周对比 |
| 周日 21:00 | 周复盘 | 回流到选题 |

**注意**：发布与互动时段要错开，不要多个自动化同时操作同一个浏览器 profile
（同一 profile 不能被两个进程同时占用）。
