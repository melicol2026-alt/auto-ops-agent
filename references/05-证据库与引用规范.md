# 05 证据库与引用规范

## 一、为什么必须有证据库

账号一旦主张"我查过""我实测过""数据显示"，就必须拿得出痕迹。
**编造的经历比不用证据更糟** —— 不用证据只是说服力弱，编造被拆穿是账号死亡。

## 二、证据来源优先级

1. **公开可核验事实**：权威媒体、官方指南、学术论文、法院判决 —— 最强，可引用可核查
2. **自己跑的实测**：采集数据、脚本运行结果 —— 强，过程可复现
3. **用户提供的真实素材** —— 强，但依赖用户供给
4. **编造的个人经历** —— **禁止**

当 1 和 3 都拿不到时，用 2（自己动手跑），**不要退而编造**。

## 三、证据入库格式

`data/evidence/facts.json`：
```json
{
  "id": "fact_001",
  "fact": "2023 年美国法院案例：律师提交的法律文书援引 6 起 AI 编造的判例，法院核查后确认全部查无此案，当事人被处罚款。",
  "source": "中国日报网转引《纽约时报》报道",
  "date": "2023",
  "usable_on_image": "6 起判例全部查无此案（来源：中国日报网转引《纽约时报》· 2023）",
  "forbidden": "不得写成『我遇到过』『我的朋友被坑了』等第一人称经历",
  "verified": true
}
```

**字段说明**：
- `usable_on_image`：图上能写的表述（已做长度与安全性裁剪）
- `forbidden`：这条事实**不能**怎么用（防止改写时越界）
- `verified`：是否已核实出处，未核实的禁止上图

## 四、引用硬规则

1. **上图必带来源行**，格式固定：`来源：媒体名 · 时间`
2. **不点名商业产品做负面指向**（避免纠纷）
3. **个案必须标注"个案"**，不能写成普遍现象
4. **引用与正文一致**：封面有证据，正文就不能是编的个人经历，否则前后矛盾
5. **先进库再上图**，禁止临时抓一个数据就画到封面上
6. **不虚构第一人称经历** —— 需要"经历感"时，写对公开信息的反应
   （如"我看到这条新闻时的反应是……"），而不是"我有次……"

## 五、禁用场景

以下内容**无论多诱人都不碰**：
- 教规避平台检测、"降 AI 率"、洗稿骗过检测、代写代改
- 伪造写作过程、伪造数据、伪造截图
- 展示登录态、Cookie、密钥、私密路径、平台后台界面
- 把自有流程描述成"抓取某平台数据"

## 六、截图脱敏清单（发布前人工过一遍）

- [ ] 无密钥、Token、API Key
- [ ] 无绝对路径、无用户名
- [ ] 无手机号、邮箱、住址、证件号
- [ ] 无他人昵称、头像、私信内容
- [ ] 无平台后台未公开界面
- [ ] 无未脱敏的客户/公司资料
