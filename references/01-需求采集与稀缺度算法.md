# 01 需求采集与稀缺度算法

## 一、采集源选型

**原则**：零登录源先跑通，登录态源作为升级档。不要因为"站内数据更准"就一上来先卡在登录环节——零登录源可以当天就开始积累数据。

| 源 | 拿到什么 | 登录 | 可用性 |
|---|---|---|---|
| 百度下拉联想 | 真实搜索需求词 | 否 | 稳定 |
| 360 下拉联想 | 同上，可交叉验证 | 否 | 稳定 |
| 必应搜索 | 公开可见供给条数 | 否 | 中文索引稀疏，常固定返回 10 条 |
| 百度搜索 | 站内供给 + 相关搜索 | 否 | **易被限流**，需检测返回条数 |
| B站搜索 API | 播放量（跨平台热度代理） | 否 | 稳定 |
| MediaCrawler | **站内真实点赞/收藏/评论/分享** | 是（扫码一次） | 长期有效 |

### 零登录方案的硬上限（实测）
- 百度会限流，返回 0 条 → 若不做检测，会被当成"无供给"，稀缺度虚高
- 必应中文对小红书索引稀疏，且固定只返回 10 条 → 所有词供给条数相同，**供给侧分辨率归零**
- 拿不到站内真实互动数据，只能用 B站播放量当代理指标

**结论**：零登录方案能证明"需求存在"，但证明不了"这个需求在目标平台还没被满足"。
必须接站内源才能闭环。这正是第 9 条铁律"采不到 ≠ 没有"的由来。

## 二、稀缺度算法

### 需求分（0–10，每项 0–2）
| 项 | 判据 |
|---|---|
| 具体问题 | 是否命中目标人群**正在发生**的具体问题（不是泛泛的"想提效"） |
| 主动搜索 | 是否在联想词里出现（有人真的会搜） |
| 可系列化 | 能否形成 3 篇以上系列 |
| 素材可得 | 素材是否真实可得（不能编） |
| 明确下一步 | 一条内容里能否给出明确下一步 |

**低于 7 分不进入草稿。**

### 供给分（0–10，即稀缺度）
```
结果条数：
  ≥15 条 → +4（供给饱和）
  8–14   → +3
  3–7    → +2
  ≤2     → +0

标题套路化率（命中"保姆级/绝了/必看/最强"等的比例）：
  ≥50% → +4（同质化严重，是机会）
  30–49% → +2
  <30% → +0

稀缺角度命中数（目标平台上有多少条是从稀缺角度写的）：
  0 条 → +2
  1–2 条 → +1
  ≥3 条 → +0
```

### 判定
- **≥4 强稀缺**：可切入，优先选题
- **2–3 中等**：靠"具体场景 + 明确边界"差异化取胜
- **≤1 放弃**

### 必须同时输出数据质量提示
报告里要有独立段落写明：
- 本次供给源分布（哪些词用百度、哪些用必应、哪些没采到）
- 有多少词的供给数据缺失
- 缺失的词**只能作观察项，禁止当作空白机会**

## 三、三个已修缺陷（别再犯）

### 缺陷 1：噪音词污染
联想词会混入完全无关的词（实测出现过"爱因斯坦""童颜针"）。
**修法**：领域白名单过滤 + 与种子词的相关性校验 + 跨源交叉验证（只出现在单一源的降权）。

### 缺陷 2：采不到当没人做（最致命）
采集失败返回 0 条 → 供给分 +0 → 稀缺度虚高到 5–6 分 → 选出一批伪机会。
**修法**：给供给结果加 `fetch_ok` 标记；`fetch_ok=False` 的词在报告里标"供给待重采"，
且**禁止**进入"强稀缺词"列表。

### 缺陷 3：相似词未合并
"ai幻觉" 和 "AI 幻觉" 被当成两个词，需求信号被稀释。
**修法**：归一化（小写、去空格、全半角统一）后再聚合。

## 四、采集频率建议
- **每日快速档**：只跑联想词 + 热度，5 分钟内，用于捕捉新增需求
- **每周全量档**：跑完整供需核查 + 周对周对比，输出稀缺度排序变化

连续采集 3 周以上才有趋势价值。单次快照只能当假设。
